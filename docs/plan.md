# BuildLog 개발 계획

## 1. 문서 목적

이 문서는 `docs/spec.md`에 적힌 BuildLog 기능을 어떤 순서로 개발하고 확인할지 정리한 실행 계획입니다.

지금은 계획만 작성합니다. 이 문서 작성으로 코드 생성, 패키지 설치, 데이터베이스 생성 또는 배포를 시작하지 않습니다.

---

## 2. 계획의 기준과 주의점

### 구현 기준

- 기능 동작의 기준은 현재 `docs/spec.md`입니다.
- 프론트엔드는 React, 백엔드는 FastAPI를 사용합니다.
- 실제 서비스의 운영 데이터베이스는 Supabase가 제공하는 PostgreSQL을 사용합니다.
- 개발 중 자동 테스트와 기능 확인에는 SQLite3를 사용합니다.
- 각 Phase는 앞 단계의 결과가 정상적으로 동작해야 시작합니다.
- 새로운 기능이 필요해 보여도 문서에 없으면 임의로 추가하지 않습니다.

### 문서 사이의 범위 차이

현재 두 문서의 서비스 범위가 서로 다릅니다.

- `docs/PRD.md`: 한 명이 사용하는 개인용 서비스이며 회원가입, 기록 공유, 댓글과 좋아요를 제외합니다.
- `docs/spec.md`: 여러 사용자의 회원가입, 공개 기록, 댓글, 좋아요와 신고를 포함합니다.

사용자는 이번 요청에서 `spec.md`를 기준으로 계획을 요청했으므로 아래 계획은 **현재 spec의 여러 사용자 기능을 기준**으로 작성합니다. 실제 개발을 시작하기 전 Phase 0에서 이 범위를 최종 확인해야 합니다.

### 현재 spec에서 추가 확인이 필요한 부분

`spec.md`는 기능 조건이 모두 정해졌다고 표시하지만, 다음 구현 기준은 명시되어 있지 않습니다.

- 운영자를 어떤 계정으로 구분할지
- 운영자가 신고 목록에 들어가는 방법
- 로그인 상태를 얼마나 유지할지
- 계정을 삭제하지 않는 것이 맞는지

이 항목은 새 기능을 제안하는 것이 아니라 이미 정한 로그인·신고·계정 범위를 정확히 구현하기 위한 확인 사항입니다.

---

## 3. 전체 개발 순서

| Phase | 목표 | 사용자가 확인할 수 있는 결과 |
|---|---|---|
| 0 | 문서와 범위 확정 | 무엇을 만들지 모순 없이 한 문장으로 설명할 수 있음 |
| 1 | 개발 기반과 데이터 구조 준비 | 프론트엔드·백엔드·DB가 로컬에서 연결됨 |
| 2 | 회원가입·로그인·권한 구현 | 가입하고 로그인해 본인 전용 화면에 들어갈 수 있음 |
| 3 | 공통 화면과 반응형 틀 구현 | PC와 휴대폰에서 메뉴와 기본 화면을 사용할 수 있음 |
| 4 | 공부 기록 구현 | 공부 기록을 만들고 읽고 수정·삭제·검색할 수 있음 |
| 5 | 할 일 구현 | 할 일을 만들고 완료 상태를 관리할 수 있음 |
| 6 | 오류 기록 구현 | 오류와 해결 방법을 기록하고 검색·필터할 수 있음 |
| 7 | 공개 기록 구현 | 다른 사용자의 공개 기록만 모아 볼 수 있음 |
| 8 | 댓글과 좋아요 구현 | 공개 공부·오류 기록에서 반응을 남길 수 있음 |
| 9 | 신고와 운영자 확인 구현 | 공개 기록·댓글을 신고하고 운영자가 확인할 수 있음 |
| 10 | 공개 범위와 권한 통합 검증 | 비공개 정보와 타인의 수정 기능이 차단됨 |
| 11 | 전체 테스트와 화면 품질 점검 | 주요 흐름이 지원 화면과 브라우저에서 안정적으로 동작함 |
| 12 | 첫 버전 마무리 | 실행 방법과 점검 결과가 정리되고 배포 가능한 상태가 됨 |

## 4. Phase 0 — 범위와 규칙 확정

### 목표

개발 중 기준이 바뀌거나 문서가 서로 충돌하지 않도록 구현 범위를 먼저 확정합니다.

### 진행 단계

1. `PRD.md`와 `spec.md`의 차이를 표로 비교합니다.
2. 단일 사용자 서비스와 여러 사용자 서비스 중 어느 문서를 최종 기준으로 삼을지 확정합니다.
3. 현재 계획대로 여러 사용자 기능을 만든다면 PRD의 제외 항목을 spec에 맞게 정리합니다.
4. 운영자 계정을 구분하는 방법과 신고 목록에 들어가는 방법을 확정합니다.
5. 로그인 유지 시간과 로그아웃 뒤 동작을 확정합니다.
6. 계정 삭제 기능은 첫 버전에 포함하지 않는지 확인합니다.
7. 제외 기능 목록을 다시 확인합니다.

### 산출물

- 서로 모순되지 않는 PRD와 spec
- 최종 기능 목록
- 확인이 끝난 권한 표
- 구현하지 않을 기능 목록

### 완료 조건

- 회원가입, 공개 기록, 댓글, 좋아요와 신고의 포함 여부가 두 문서에서 같습니다.
- 일반 사용자와 운영자가 볼 수 있는 화면을 구분할 수 있습니다.
- 개발자가 추측해야 하는 계정·로그인·신고 조건이 남아 있지 않습니다.

## 5. Phase 1 — 개발 기반과 데이터 구조

### 목표

각 기능을 같은 방식으로 개발하고 테스트할 수 있도록 프로젝트의 기본 연결과 저장 구조를 준비합니다.

### 백엔드 작업

1. FastAPI 애플리케이션의 시작 구조를 만듭니다.
2. 환경 설정에서 데이터베이스 주소와 비밀값을 읽도록 준비합니다.
3. 테스트 환경에서는 SQLite3에 연결하고, 운영 환경에서는 Supabase에 연결하도록 환경별 데이터베이스 설정을 나눕니다.
4. 같은 데이터 구조 변경 이력을 SQLite3 테스트 환경과 Supabase 운영 환경에 적용할 수 있게 준비합니다.
5. 서버가 실행 중인지 확인하는 간단한 상태 확인 경로를 준비합니다.
6. 공통 성공·실패 응답 형식을 정합니다.
7. 날짜와 시간은 한 기준으로 저장하고 화면 표시 기준을 정합니다.

### 프론트엔드 작업

1. React 애플리케이션의 시작 구조를 만듭니다.
2. 화면 이동 구조와 공통 데이터 요청 방식을 준비합니다.
3. 로딩, 빈 목록, 실패 안내에 사용할 공통 화면 요소를 준비합니다.
4. 입력창, 버튼, 확인창, 카드와 상태 표시의 기본 모양을 준비합니다.

### 데이터 구조 작업

아래 정보가 서로 연결되도록 데이터 구조를 설계합니다.

- 사용자: 이메일, 안전하게 처리한 비밀번호, 닉네임, 작성·수정 시각
- 공부 기록: 작성자, 제목, 내용, 공개 여부, 작성·수정 시각
- 할 일: 작성자, 제목, 완료 여부, 완료 시각, 공개 여부, 작성·수정 시각
- 오류 기록: 작성자, 오류 제목, 오류 내용, 해결 방법, 해결 여부, 해결 시각, 공개 여부, 작성·수정 시각
- 댓글: 작성자, 대상 기록, 내용, 작성·수정 시각
- 좋아요: 누른 사용자, 대상 기록
- 신고: 신고한 사용자, 신고 대상, 신고 이유, 신고 시각

### 반드시 적용할 저장 규칙

- 같은 이메일은 한 번만 저장합니다.
- 같은 닉네임은 한 번만 저장합니다.
- 한 사용자는 같은 기록에 좋아요를 한 번만 저장합니다.
- 한 사용자는 같은 대상을 한 번만 신고합니다.
- 댓글·좋아요·신고가 연결될 수 있는 대상 종류를 spec 범위로 제한합니다.
- 기록을 삭제할 때 연결된 댓글, 좋아요와 신고를 어떻게 처리할지는 Phase 0에서 확정한 기준을 따릅니다.

### 데이터베이스 환경 원칙

- SQLite3는 테스트 전용으로 사용하며 실제 서비스 데이터를 저장하지 않습니다.
- Supabase 연결 정보는 환경 설정으로만 관리하고 소스 코드에 적지 않습니다.
- 데이터 저장 기능은 SQLite3와 Supabase에서 같은 결과가 나와야 합니다.
- 두 데이터베이스에서 문법이나 동작이 다른 기능에 의존하지 않도록 주의합니다.
- 각 기능은 SQLite3 자동 테스트를 먼저 통과한 뒤 Supabase 환경에서 연결·권한·저장 결과를 다시 확인합니다.

### 검증

- 프론트엔드가 백엔드 상태를 정상적으로 확인하는지 점검합니다.
- 백엔드가 테스트 중 SQLite3에 연결되고 기본 데이터 저장·조회가 되는지 점검합니다.
- 백엔드가 Supabase에 연결되고 같은 데이터 구조로 기본 저장·조회가 되는지 별도로 점검합니다.
- SQLite3에서 통과한 주요 저장 규칙이 Supabase에서도 동일하게 동작하는지 확인합니다.
- 중복 이메일, 닉네임, 좋아요와 신고가 저장 단계에서도 막히는지 점검합니다.
- 비밀값이 소스 코드나 문서에 들어가지 않았는지 점검합니다.

### 완료 조건

- React와 FastAPI가 로컬에서 함께 실행되고, 테스트는 SQLite3를 사용합니다.
- Supabase 연결 정보를 설정하면 운영 데이터베이스 연결도 확인할 수 있습니다.
- 데이터 구조 변경을 반복 적용할 수 있습니다.
- 아직 사용자 기능이 없어도 다음 Phase를 안전하게 개발할 기반이 갖춰집니다.

## 6. Phase 2 — 회원가입, 로그인과 기본 권한

### 목표

사용자가 자신의 계정을 만들고 로그인하며, 본인의 데이터만 관리할 수 있는 기반을 완성합니다.

### 구현 순서

1. 회원가입 입력과 저장
2. 이메일·닉네임 중복 확인
3. 입력 길이와 문자 조건 확인
4. 안전한 비밀번호 저장
5. 로그인과 로그인 실패 처리
6. 로그아웃
7. 로그인하지 않은 사용자의 기록 화면 접근 차단
8. 닉네임 변경
9. 본인 데이터와 타인 데이터 권한 구분

### 회원가입 조건

- 이메일은 일반적인 이메일 형식이어야 합니다.
- 비밀번호는 8~64자입니다.
- 닉네임은 2~20자입니다.
- 닉네임에는 한글, 영문, 숫자와 밑줄만 사용합니다.
- 이메일과 닉네임 앞뒤 공백을 제거합니다.
- 실패하면 이메일과 닉네임은 유지하고 비밀번호만 지웁니다.
- 성공하면 로그인 화면으로 이동합니다.
- 이메일 확인과 비밀번호 찾기는 만들지 않습니다.

### 닉네임 변경 조건

- 로그인한 사용자는 자신의 닉네임만 바꿀 수 있습니다.
- 회원가입과 같은 길이, 문자와 중복 조건을 적용합니다.
- 닉네임을 바꾸면 과거 공개 기록과 댓글에도 새 닉네임이 보입니다.

### 검증

- spec에 적힌 최소·최대 길이 경계값을 모두 확인합니다.
- 중복 이메일과 닉네임으로 가입할 수 없는지 확인합니다.
- 올바른 정보와 틀린 정보로 로그인 결과를 비교합니다.
- 로그인 전에는 기록 화면을 열 수 없는지 확인합니다.
- 한 사용자가 다른 사용자의 계정 정보를 바꿀 수 없는지 확인합니다.

### 완료 조건

- 회원가입 → 로그인 → 닉네임 변경 → 로그아웃 흐름이 이어서 동작합니다.
- 비밀번호가 화면, 로그 또는 데이터베이스에 읽을 수 있는 원문으로 남지 않습니다.
- 로그인하지 않은 요청과 권한이 없는 요청이 모두 차단됩니다.

## 7. Phase 3 — 공통 화면, 이동과 반응형 틀

### 목표

이후 기능을 같은 화면 구조 안에서 추가할 수 있도록 공통 사용자 화면을 만듭니다.

### 진행 단계

1. 로그인 전 화면과 로그인 후 화면을 나눕니다.
2. 내 기록 홈, 공부 기록, 할 일, 오류 기록과 공개 기록으로 이동하는 메뉴를 만듭니다.
3. 계정 설정과 로그아웃 진입점을 둡니다.
4. 공통 카드, 목록, 입력 폼, 실패 안내와 삭제 확인창을 만듭니다.
5. 밝은 배경과 읽기 쉬운 카드 중심의 기본 디자인을 적용합니다.
6. 360px 너비부터 큰 화면까지 내용이 겹치지 않게 배치합니다.

### 검증

- 모든 메뉴가 올바른 빈 화면으로 이동하는지 확인합니다.
- 로그인 상태에 따라 보이는 메뉴가 달라지는지 확인합니다.
- 360px 화면에서 입력칸과 버튼이 화면 밖으로 나가지 않는지 확인합니다.
- 키보드만으로 주요 입력과 버튼을 사용할 수 있는지 확인합니다.

### 완료 조건

- 실제 기록 기능을 붙일 공통 화면이 준비됩니다.
- PC와 휴대폰에서 같은 기능에 접근할 수 있습니다.

---

## 8. Phase 4 — 공부 기록

### 목표

공부 기록의 작성, 목록, 상세, 검색, 수정, 삭제와 공개 범위를 완성합니다.

### 구현 순서

1. 공부 기록 작성 화면
2. 제목·내용 입력 조건
3. 비공개 기본값과 공개 여부 저장
4. 내 공부 기록 목록과 최근 작성 순 정렬
5. 상세 읽기
6. 제목·내용 검색
7. 수정과 수정 시각 표시
8. 삭제 확인과 삭제
9. 작성자와 다른 사용자의 권한 차단

### 입력과 동작 기준

- 제목은 1~100자이며 필수입니다.
- 내용은 1~5,000자이며 필수입니다.
- 제목과 내용의 앞뒤 공백을 제거합니다.
- 공개 여부를 선택하지 않으면 비공개로 저장합니다.
- 저장 성공 후 공부 기록 목록으로 이동합니다.
- 검색어가 비어 있으면 전체 내 공부 기록을 보여줍니다.
- 작성자만 수정·삭제할 수 있습니다.

### 검증

- 제목과 내용의 최소·최대·초과 길이를 확인합니다.
- 공백만 입력한 기록이 저장되지 않는지 확인합니다.
- 저장 실패 후 입력값이 남는지 확인합니다.
- 공개·비공개 기록이 내 목록에는 모두 보이는지 확인합니다.
- 다른 사용자가 비공개 기록을 보거나 기록을 수정·삭제할 수 없는지 확인합니다.
- 수정·삭제 성공과 실패 결과를 확인합니다.

### 완료 조건

- 한 사용자가 자신의 공부 기록 전체 흐름을 막힘없이 사용할 수 있습니다.
- 다른 사용자는 공개 기록을 읽는 것 외에는 변경할 수 없습니다.

## 9. Phase 5 — 할 일

### 목표

할 일 작성, 목록, 상태 필터, 완료 처리, 수정과 삭제를 완성합니다.

### 구현 순서

1. 할 일 작성
2. 내 할 일 목록
3. 전체·남은 일·완료한 일 필터
4. 완료와 완료 취소
5. 완료 시각 저장과 취소 시 제거
6. 수정 시각 표시
7. 삭제 확인과 삭제
8. 공개 범위와 작성자 권한

### 입력과 동작 기준

- 제목은 1~100자이며 필수입니다.
- 새 할 일은 미완료와 비공개 상태가 기본입니다.
- 목록에서는 미완료 항목을 먼저 보여줍니다.
- 같은 상태에서는 최근 작성한 항목을 먼저 보여줍니다.
- 완료하면 완료 날짜와 시간을 저장합니다.
- 완료를 취소하면 완료 날짜와 시간을 지웁니다.
- 할 일 마감일, 중요도와 내 할 일 검색은 만들지 않습니다.

### 검증

- 제목 길이와 공백 규칙을 확인합니다.
- 세 가지 필터의 결과를 확인합니다.
- 완료와 취소 때 상태와 완료 시각이 함께 바뀌는지 확인합니다.
- 다른 사용자가 공개 할 일을 읽을 수 있지만 변경할 수 없는지 확인합니다.
- 수정·삭제 실패 시 기존 값과 입력값이 올바르게 유지되는지 확인합니다.

### 완료 조건

- 사용자가 남은 일과 끝난 일을 정확히 나눠 관리할 수 있습니다.
- 공개 여부와 작성자 권한이 공부 기록과 같은 원칙으로 동작합니다.

## 10. Phase 6 — 오류 기록

### 목표

오류와 해결 방법을 작성하고 해결 상태를 관리하며 검색·필터할 수 있게 합니다.

### 구현 순서

1. 오류 기록 작성
2. 미해결 기본 상태
3. 목록과 최근 작성 순 정렬
4. 전체·미해결·해결 필터
5. 제목·오류 내용 검색
6. 상세 읽기
7. 해결 방법 입력과 해결 처리
8. 해결 취소
9. 수정과 삭제
10. 공개 범위와 작성자 권한

### 입력과 동작 기준

- 오류 제목은 1~100자이며 필수입니다.
- 오류 내용은 1~5,000자이며 필수입니다.
- 해결 방법은 최대 5,000자입니다.
- 처음에는 미해결 상태로 저장합니다.
- 해결 상태로 바꾸려면 해결 방법이 필요합니다.
- 해결하면 해결 날짜와 시간을 저장합니다.
- 다시 미해결로 바꾸면 해결 방법은 남기고 해결 시각만 지웁니다.
- 공개 여부의 기본값은 비공개입니다.

### 검증

- 제목, 오류 내용과 해결 방법의 길이 경계값을 확인합니다.
- 해결 방법 없는 해결 처리가 차단되는지 확인합니다.
- 해결과 해결 취소 시 저장 값이 spec대로 바뀌는지 확인합니다.
- 세 가지 필터와 제목·내용 검색 결과를 확인합니다.
- 수정·삭제와 작성자 권한을 확인합니다.

### 완료 조건

- 미해결 오류 등록부터 해결 방법 기록까지 전체 흐름이 이어집니다.
- 검색과 필터로 과거 오류를 다시 찾을 수 있습니다.

## 11. Phase 7 — 공개 기록

### 목표

로그인한 사용자가 다른 사용자의 공개 기록만 안전하게 찾아볼 수 있게 합니다.

### 구현 순서

1. 공개 기록 목록
2. 최근 작성 순 정렬
3. 공부 기록·할 일·오류 기록 종류 필터
4. 종류별 검색 대상 적용
5. 공개 기록 상세 보기
6. 로그인하지 않은 사용자 접근 차단
7. 비공개 전환 즉시 목록 제외

### 검색 기준

- 공부 기록: 제목과 내용
- 할 일: 제목
- 오류 기록: 오류 제목, 오류 내용과 해결 방법
- 빈 검색어: 전체 공개 기록
- 검색 결과에는 공개 기록만 포함

### 검증

- 세 종류의 공개 기록만 공개 목록에 나타나는지 확인합니다.
- 비공개 기록이 목록, 검색과 직접 접근에서 모두 차단되는지 확인합니다.
- 종류별 검색 대상과 필터를 확인합니다.
- 타인의 공개 기록에서 수정·삭제 버튼이 동작하지 않는지 확인합니다.
- 비공개로 전환한 기록이 즉시 공개 화면에서 사라지는지 확인합니다.

### 완료 조건

- 로그인한 사용자는 공개 기록을 찾고 읽을 수 있습니다.
- 공개 여부가 모든 목록, 검색과 상세 접근에 일관되게 적용됩니다.

## 12. Phase 8 — 댓글과 좋아요

### 목표

공개된 공부 기록과 오류 기록에서만 댓글과 좋아요를 사용할 수 있게 합니다.

### 댓글 구현 순서

1. 공개 공부·오류 기록의 댓글 목록
2. 1~500자 댓글 작성
3. 오래된 댓글부터 정렬
4. 댓글 작성자의 수정·삭제
5. 기록 작성자의 댓글 삭제
6. 비공개 전환 시 댓글 숨김과 재공개 시 복원

### 좋아요 구현 순서

1. 좋아요 등록
2. 다시 눌러 취소
3. 사용자별 중복 방지
4. 현재 사용자의 좋아요 상태 표시
5. 전체 좋아요 수 표시
6. 비공개 전환 시 좋아요와 개수 숨김 및 재공개 시 복원

### 제외 조건

- 공개된 할 일에는 댓글과 좋아요를 제공하지 않습니다.
- 댓글 답글은 만들지 않습니다.

### 검증

- 댓글 길이, 공백 제거, 실패 시 입력 유지와 권한을 확인합니다.
- 댓글 작성자와 기록 작성자의 삭제 권한 차이를 확인합니다.
- 타인의 댓글 수정이 차단되는지 확인합니다.
- 좋아요를 중복 저장할 수 없는지 확인합니다.
- 공개 상태를 바꿔도 댓글과 좋아요 정보는 삭제되지 않고 보이기만 달라지는지 확인합니다.

### 완료 조건

- 공개 공부·오류 기록에서 댓글과 좋아요가 spec대로 동작합니다.
- 공개 할 일과 비공개 기록에서는 두 기능을 사용할 수 없습니다.

## 13. Phase 9 — 신고와 운영자 확인

### 목표

로그인한 사용자가 공개 기록과 댓글을 신고하고, 운영자만 신고 내용을 확인할 수 있게 합니다.

### 구현 순서

1. 공개 기록의 신고 버튼
2. 댓글의 신고 버튼
3. 1~500자 신고 이유 입력
4. 같은 사용자·대상 중복 신고 차단
5. 신고 접수 안내
6. 운영자 전용 신고 목록과 내용 보기
7. 일반 사용자의 신고 목록 접근 차단

### 동작 기준

- 신고만으로 기록이나 댓글을 자동 삭제하지 않습니다.
- 신고 실패 시 입력한 신고 이유를 유지합니다.
- 신고 내용은 일반 사용자에게 공개하지 않습니다.
- 첫 버전에서는 신고 처리 상태, 제재와 자동 숨김을 만들지 않습니다.

### 검증

- 공개 기록과 댓글을 각각 신고할 수 있는지 확인합니다.
- 같은 사용자가 같은 대상을 두 번 신고할 수 없는지 확인합니다.
- 신고 이유의 길이와 공백 규칙을 확인합니다.
- 일반 사용자가 신고 목록을 볼 수 없는지 확인합니다.
- 운영자는 신고를 확인만 할 수 있고 처리 상태를 바꿀 수 없는지 확인합니다.
- 신고 직후 대상이 자동으로 사라지지 않는지 확인합니다.

### 완료 조건

- 신고 접수와 운영자 확인이 권한에 맞게 동작합니다.
- spec에 없는 신고 처리 기능이 추가되지 않습니다.

## 14. Phase 10 — 공개 범위와 권한 통합 검증

### 목표

각 기능을 따로 구현하면서 생길 수 있는 개인정보 노출과 권한 오류를 전체 흐름에서 찾아 수정합니다.

### 역할별 권한 점검

| 대상 | 작성자 | 다른 로그인 사용자 | 로그인하지 않은 사용자 | 운영자 |
|---|---|---|---|---|
| 비공개 기록 | 읽기·수정·삭제 | 접근 불가 | 접근 불가 | spec에 정한 범위만 허용 |
| 공개 기록 | 읽기·수정·삭제 | 읽기 | 접근 불가 | 읽기 |
| 댓글 | 본인 댓글 수정·삭제 | 본인 댓글 작성·수정·삭제 | 접근 불가 | spec에 정한 범위만 허용 |
| 타인의 댓글 | 기록 작성자는 삭제 가능 | 수정·삭제 불가 | 접근 불가 | spec에 정한 범위만 허용 |
| 좋아요 | 본인 좋아요 등록·취소 | 본인 좋아요 등록·취소 | 접근 불가 | 일반 사용자와 동일 |
| 신고 내용 | 접근 불가 | 접근 불가 | 접근 불가 | 읽기 |

### 집중 점검 항목

1. 화면에서 버튼을 숨기는 것뿐 아니라 실제 요청도 권한 없이 처리되지 않는지 확인합니다.
2. 비공개 기록 주소를 직접 열어도 내용이 노출되지 않는지 확인합니다.
3. 검색 결과와 공개 목록에 비공개 기록이 섞이지 않는지 확인합니다.
4. 기록을 비공개로 바꿨을 때 댓글과 좋아요가 다른 사용자에게 즉시 숨겨지는지 확인합니다.
5. 다시 공개했을 때 기존 댓글과 좋아요가 복원되는지 확인합니다.
6. 닉네임 변경이 과거 공개 기록과 댓글에 반영되는지 확인합니다.
7. 삭제된 대상에 댓글, 좋아요 또는 신고가 잘못 노출되지 않는지 확인합니다.

### 완료 조건

- 역할별 허용·차단 결과가 표와 일치합니다.
- 비공개 데이터가 화면, 검색 결과와 직접 접근 어디에서도 노출되지 않습니다.

## 15. Phase 11 — 전체 테스트와 화면 품질

### 목표

기능별 확인 항목과 실제 사용자 흐름을 함께 점검해 첫 버전의 안정성을 확보합니다.

### 자동 확인

- 입력값 최소·최대 길이와 공백 처리
- 중복 이메일, 닉네임, 좋아요와 신고 차단
- 로그인과 권한 차단
- 각 기록의 작성·조회·수정·삭제
- 공개·비공개 변경
- 검색, 정렬과 필터
- 완료·해결 상태와 날짜·시간 변경
- 댓글·좋아요·신고 권한

### 사용자 흐름 확인

1. 사용자 A와 사용자 B가 각각 가입합니다.
2. A가 세 종류의 공개·비공개 기록을 만듭니다.
3. B가 공개 기록만 볼 수 있는지 확인합니다.
4. B가 공개 공부·오류 기록에 댓글과 좋아요를 남깁니다.
5. A가 댓글 관리와 공개 범위 변경을 확인합니다.
6. B가 공개 기록과 댓글을 신고합니다.
7. 일반 사용자와 운영자의 신고 접근 차이를 확인합니다.
8. A가 기록을 수정·삭제한 뒤 모든 관련 화면을 다시 확인합니다.

### 화면과 브라우저 확인

- 너비 360px 이상의 휴대폰 화면
- 일반적인 컴퓨터 화면
- Chrome 최신 두 버전
- Edge 최신 두 버전
- Safari 최신 두 버전
- 긴 제목, 긴 내용, 빈 목록과 실패 안내
- 버튼과 글자가 겹치거나 화면 밖으로 나가지 않는지

### 회귀 확인

수정한 기능 때문에 이미 끝난 기능이 다시 고장 나지 않았는지 Phase 2부터 Phase 10까지의 핵심 확인 항목을 반복합니다.

### 완료 조건

- spec의 모든 ‘확인 방법’ 항목이 통과합니다.
- 심각한 데이터 손실, 권한 노출과 주요 흐름 중단 문제가 없습니다.
- 지원 대상 화면과 브라우저에서 주요 기능을 사용할 수 있습니다.

## 16. Phase 12 — 첫 버전 마무리

### 목표

다른 날 다시 프로젝트를 열어도 실행하고 확인할 수 있으며, 배포 여부를 결정할 수 있는 상태로 만듭니다.

### 진행 단계

1. 로컬 실행 방법을 문서화합니다.
2. 필요한 환경 설정 항목을 비밀값 없이 `.env.example`에 정리합니다.
3. SQLite3 테스트 데이터베이스와 Supabase 운영 데이터베이스의 준비 방법을 각각 문서화합니다.
4. 같은 데이터 구조 변경을 두 환경에 적용하는 순서를 문서화합니다.
5. 테스트 실행 방법과 최종 결과를 정리합니다.
6. 첫 번째 버전에서 제외한 기능이 들어가지 않았는지 확인합니다.
7. 알려진 제한이나 남은 문제가 있으면 문서에 적습니다.
8. SQLite3 테스트와 Supabase 환경 확인이 모두 끝난 뒤에만 실제 배포 단계를 별도로 진행합니다.

### 최종 완료 기준

- 새 환경에서 문서만 보고 서비스를 실행할 수 있습니다.
- 회원가입부터 신고 확인까지 핵심 사용자 흐름이 동작합니다.
- 모든 권한과 공개 범위 확인이 통과합니다.
- 비밀값이 저장소에 포함되지 않습니다.
- 이메일 확인, 비밀번호 찾기, 할 일 마감일·중요도·검색과 댓글 답글이 들어가지 않았습니다.
- 첫 버전의 기능 목록과 실제 화면이 일치합니다.

## 18. Phase 진행 원칙

각 Phase는 다음 순서로 진행합니다.

1. 해당 Phase의 spec 조건을 다시 읽습니다.
2. 화면에서 필요한 행동과 저장할 정보를 연결합니다.
3. 백엔드 저장·조회와 권한을 먼저 확인합니다.
4. 프론트엔드 화면과 연결합니다.
5. 정상 동작, 잘못된 입력, 처리 실패와 권한을 확인합니다.
6. 완료 조건을 모두 통과한 뒤 다음 Phase로 이동합니다.

하나의 Phase가 끝나지 않은 상태에서 뒤 기능을 동시에 넓게 만들지 않습니다. 특히 공개 기록, 댓글, 좋아요와 신고는 회원·기록·권한 기능이 안정된 뒤 진행합니다.
